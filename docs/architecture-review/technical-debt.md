# Maintainability, legacy inventory and safe next steps

[Report index](README.md) · [Module map](module-map.md) · [Execution flows](execution-flows.md) · [Learning guide](learning-guide.md)

Baseline: public main `fe035ee…`; explicitly labeled research overlays are separate. **No runtime changes, removals or archives were made.** Priorities express maintenance value, not an invented severity score. P1 = protect authority and reduce concrete cross-layer coupling before substantial integration work; P2 = useful scoped improvements; P3 = optional cleanup or later isolation. Confidence describes the observation, not the likelihood of a hypothetical bug.

## Cohesion and coupling assessment

| Criterion | Evidence-based assessment | Implication |
|---|---|---|
| Cohesion / responsibility | Policy and B4 ranking are pure decision modules. Dispatcher concentrates recovery semantics. Unit of work concentrates transaction-local integrity. `TriageService` additionally owns schema definitions, two persistence modes, lifecycle orchestration and historical projections | Preserve the cohesive command/storage mechanisms. Consider internal service command families only where responsibility and tests give a clear seam |
| Dependency direction | One six-file value-declaration SCC crosses runtime, timeout/provider helpers and knowledge service. `domain.ts` imports a taxonomy inference schema. Diagnosis review imports service-owned schema | Move foundational contracts/errors downward only when callers can keep the same behavior and public exports. Do not create a large generic utility module |
| Interfaces / authority | `PreparedCommandDefinition` hides identity/in-flight/transaction recovery well. `HybridShadowCaptureSink` is optional and provider-neutral. Operational repository mutation methods reject direct writes | Strong seams already exist; future HYBRID work should consume them without bypassing the service/unit of work |
| Test isolation | Injectable providers, clock/scheduler/store interfaces, synthetic fixtures and SQLite temp stores allow meaningful focused tests. Runtime imports nevertheless pull broad modules into utility/provider tests | Reduce composition imports; keep parity/replay tests alongside pure tests. Focused successes do not prove all deployments or native bindings work |
| Failure handling | Explicit stale/replay/transaction failures, advisory stage traces, outbox retries and capture containment are visible. B5 adapter intentionally compresses unexpected semantic failures to `UNAVAILABLE` | Keep safe public codes. If diagnosability needs improvement, add bounded internal distinctions without persisting raw provider messages |
| State ownership | Operational, learning, retrieval and shadow state have different owners. Outbox bridges DBs. Versioned snapshots/references retain provenance | Do not merge these stores for convenience or introduce an unsupported cross-DB transaction claim |
| Duplication / complexity | Legacy and operational orchestration variants, repeated provider transport/error handling, content-specific response branches and embedded browser code | Deduplicate only behavior with matching contracts. Research provider/schema variants and historical replay support are not interchangeable |
| Navigability | Directory `approval-desk/` contains domain decisions, provider contracts, evaluations, HTTP and UI. Some retrieval functions compress substantial logic into single lines | Directory names and line counts are poor guides to authority or complexity; use command/symbol maps and explanatory summaries |

## Prioritized finding register

### AR-01 — Runtime-defined error creates an inward dependency cycle

**P1 · Refactor · Verified structural finding.** `StartupConfigError` is defined at [src/runtime.ts:71](https://github.com/MatiasLaukka/Support-Ticket-Triage-MCP/blob/fe035ee383b6f9df1869104f8a623609d025023b/src/runtime.ts#L71), while [src/utils/parse-openai-timeout.ts:1](https://github.com/MatiasLaukka/Support-Ticket-Triage-MCP/blob/fe035ee383b6f9df1869104f8a623609d025023b/src/utils/parse-openai-timeout.ts#L1) and [src/approval-desk/draft-response-provider.ts:31](https://github.com/MatiasLaukka/Support-Ticket-Triage-MCP/blob/fe035ee383b6f9df1869104f8a623609d025023b/src/approval-desk/draft-response-provider.ts#L31) import it. Runtime imports both parsing and provider construction. The six-file SCC also includes `controlled-evaluation-providers.ts`, `knowledge-evolution/candidate-draft-provider.ts` and `knowledge-evolution/service.ts`; candidate drafting imports `classifyAiFailure` from the response provider.

This makes low-level parsing/provider imports depend on composition and unrelated store/service modules. It increases the surface a developer must understand to test a timeout or error case. The generated value-declaration SCC and exact edges are in [static-summary.json](evidence/static-summary.json) and [imports.tsv](evidence/imports.tsv). No initialization crash was observed; compiler/focused tests passed.

**Candidate change:** relocate the startup configuration error to a small foundational module, preserving existing exports/identity where compatibility requires. Then consider extracting provider-neutral failure classification only if multiple existing callers can keep the same contract. Do this in two independently reviewed tasks, not as an all-provider rewrite. Validate [test/openai-timeout-config.test.ts](https://github.com/MatiasLaukka/Support-Ticket-Triage-MCP/blob/fe035ee383b6f9df1869104f8a623609d025023b/test/openai-timeout-config.test.ts), [test/runtime.test.ts](https://github.com/MatiasLaukka/Support-Ticket-Triage-MCP/blob/fe035ee383b6f9df1869104f8a623609d025023b/test/runtime.test.ts), [test/openai-draft-provider.test.ts](https://github.com/MatiasLaukka/Support-Ticket-Triage-MCP/blob/fe035ee383b6f9df1869104f8a623609d025023b/test/openai-draft-provider.test.ts), [test/openai-knowledge-candidate-provider.test.ts](https://github.com/MatiasLaukka/Support-Ticket-Triage-MCP/blob/fe035ee383b6f9df1869104f8a623609d025023b/test/openai-knowledge-candidate-provider.test.ts), and entrypoint error behavior. Re-run static SCC analysis and inspect emitted imports.

### AR-03 — Foundation schemas depend on inference and service implementation

**P2 · Refactor selectively · Verified type/value relationships.** [src/domain.ts:6](https://github.com/MatiasLaukka/Support-Ticket-Triage-MCP/blob/fe035ee383b6f9df1869104f8a623609d025023b/src/domain.ts#L6) value-imports `TaxonomyInferenceCandidateSchema` from `taxonomy-inference.ts`; taxonomy inference type-imports `Ticket` and `TicketClassification`. `DiagnosisContextSchema` lives in the service implementation yet is consumed by `diagnosis-review.ts`. `retrieval/types.ts:1` and `retrieval/ranking-types.ts:1` import each other's types.

The 7-file and 32-file type-inclusive SCCs show interface coupling, not equivalent runtime cycles. ### AR-08 — Shadow contract is intentionally incomplete for operational diagnosis

**P1 safety prerequisite · Retain current isolation; replace after validation only · Verified limitation.** The B5 adapter rejects diagnosis mode ([src/reasoning/b5-hybrid-reasoning-provider.ts:31](https://github.com/MatiasLaukka/Support-Ticket-Triage-MCP/blob/fe035ee383b6f9df1869104f8a623609d025023b/src/reasoning/b5-hybrid-reasoning-provider.ts#L31)). **Next requirement:** comparative value evidence first. Tests must cover malformed/unsupported outputs, stale evidence, capture failure isolation, revision/reply races, no provider rerun on replay, scoped human approval, and rollback. This audit does not supply diagnostic ground truth or claim an H6 result.

## Safe sequence of follow-up tasks

Correctness/safety requirements are separated from optional maintenance below. These are **proposals, not authorization to implement them**. Each task should start from a verified current baseline in a suitable isolated worktree and preserve dirty/frozen state.

|---|---|---|---|---|
